# Режим декомпозиции ТЗ

Когда активирован этот скилл — ты в режиме ПОДГОТОВКИ. Твоя цель: не выполнять, а понять. Превратить большое сырое ТЗ в структурированную карту которую команда сможет выполнять пошагово.

**Никакой реализации до конца декомпозиции.** Сначала — полная карта. Потом — выполнение.

---

## Что читаешь перед стартом

1. **ТЗ** — файл из `tz/` или текст от пользователя. Читать полностью, без пропусков.
2. **PROJECT_CONTEXT.md** — если уже заполнен, смотришь что уже известно о стеке.
3. **REQUIREMENTS.md** — если уже есть записи, не затираешь — дополняешь.

---

## 6 проходов декомпозиции

Строго по порядку. Каждый проход — отдельный шаг. Не смешивать.

**Сквозное правило: ТЗ всегда открыто.** На каждом проходе — перед тем как записать результат — сверяйся с оригинальным ТЗ. Не по памяти, а буквально перечитай нужный кусок. Память врёт, файл — нет.

---

### Проход 1 — Карта доменов

**Цель:** понять крупную структуру, не фичи.

1. Читаешь ТЗ целиком
2. Выделяешь смысловые блоки — домены. Не "добавить авторизацию", а "Авторизация". Не функции, а области.
3. Для каждого домена — 1-2 предложения: что это такое, зачем нужно

**Типичные домены:** Авторизация, Пользователи, Каталог/Товары, Заказы, Платежи, Уведомления, Аналитика, Администрирование, Интеграции, Публичное API.

**Перед записью:** перечитай ТЗ ещё раз — не упустил ли домен? Есть ли в ТЗ блоки которые не попали ни в один домен?

**Результат:** список 5-15 доменов. Записываешь в `REQUIREMENTS.md` секция "Карта доменов".

**Агенты на этом проходе:**
- Если есть существующий код → запускаешь Пашу: "Покажи какие домены уже реализованы в кодовой базе"
- Параллельно с Пашей, если домен незнакомый → запускаешь Костю: "Research по домену X — как обычно устроен, стандартные подходы"

---

### Проход 2 — Фичи по доменам

**Цель:** для каждого домена — конкретный список функций.

1. Берёшь каждый домен из прохода 1
2. Вытаскиваешь из ТЗ все упоминания этого домена
3. Формулируешь конкретные фичи: глагол + объект. "Регистрация по email", "Логин через Google", "Сброс пароля".
4. Если в ТЗ что-то неоднозначно — помечаешь вопросом: "[?] Нужна ли двухфакторная аутентификация?"

**Перед записью:** для каждого домена вернись в ТЗ и перечитай все упоминания этого домена. Сверь: каждое упоминание из ТЗ стало фичей? Нет ли мелких деталей ("а ещё нужно чтобы...") которые потерялись?

**Результат:** под каждым доменом — список фич. Дописываешь в `REQUIREMENTS.md`.

**Агенты на этом проходе:**
- Паша (если есть код): "Какие фичи домена X уже реализованы? Покажи конкретно"
- Макс: "По домену X (безопасность/платежи) — какие функции нельзя пропускать даже в v1?"

---

### Проход 3 — Скоп с пользователем

**Цель:** каждая фича должна попасть в v1, v2 или "вне скопа". Ничего не теряется.

1. Выводишь пользователю полный список фич сгруппированных по доменам
2. Задаёшь **один** вопрос: "Вот всё что я нашёл в ТЗ. Отметь что в v1 (делаем сейчас), что в v2 (потом), что вообще не нужно."
3. Если у пользователя есть вопросы по конкретным фичам — отвечаешь, уточняешь
4. Записываешь решение в `REQUIREMENTS.md` секции v1/v2/вне скопа

**Железное правило:** каждая фича из ТЗ должна быть классифицирована. Если пользователь не ответил по какой-то фиче — уточни, не додумывай. После классификации — пересчитай: количество фич в v1 + v2 + вне скопа должно равняться общему количеству фич из прохода 2. Если не сходится — что-то потеряно.

**Агенты:** никого не запускаешь. Это разговор с пользователем.

---

### Проход 4 — Зависимости

**Цель:** понять в каком порядке нужно делать v1-фичи. Что от чего зависит.

1. Берёшь только v1-фичи из прохода 3
2. Запускаешь Серёгу (innovator): передаёшь список v1-фич и просишь построить граф зависимостей

**Prompt для Серёги:**
```
Задача: определить зависимости между фичами для правильной очерёдности реализации.
Список v1-фич по доменам: [вставляешь список]
Вопрос: что от чего зависит? Что нельзя делать пока не готово X?
Нужен граф: фича → зависит от [фича A, фича B] или "независима"
Важно: вертикальные срезы (одна фича end-to-end) параллелятся лучше чем горизонтальные слои (сначала все модели, потом все API).
```

3. По результату от Серёги — Дима расставляет зависимости

**Агенты:**
- Серёга (innovator) — строит граф зависимостей
- Макс (security-auditor) — если есть платежи/авторизация: "Что по безопасности нельзя откладывать на v2?"

---

### Проход 5 — Фазы и волны

**Цель:** ROADMAP с фазами, волнами и зависимостями.

1. Берёшь v1-фичи с зависимостями из прохода 4
2. Группируешь в фазы по принципу:
   - Одна фаза = логически завершённый блок который можно задеплоить и протестировать
   - Фазы идут последовательно
   - Фазы 1-3 обычно: фундамент (модели, БД, аутентификация) → ядро (основная бизнес-логика) → оболочка (UI, интеграции, уведомления)
3. Внутри каждой фазы — волны по зависимостям:
   - Волна 1: задачи без зависимостей (параллельно)
   - Волна 2: задачи зависящие от волны 1 (параллельно между собой)
   - И так далее
4. Записываешь в `ROADMAP.md`
5. Заполняешь `PROJECT_CONTEXT.md` если стек/архитектура стали ясны

**Показываешь пользователю итог:**
```
Карта готова. Вот что получилось:

Фаза 1 — [название]: [список фич]
Фаза 2 — [название]: [список фич]
...

Порядок волн в фазе 1:
  Волна 1 (параллельно): [задачи]
  Волна 2 (зависит от волны 1): [задачи]

Согласен? Или поменяем что-то?
```

Только после подтверждения пользователя — переходим к верификации.

---

### Проход 6 — Верификация полноты

**Цель:** гарантировать что ни одно требование из оригинального ТЗ не потеряно.

Это самый критичный проход. Всё предыдущее — декомпозиция. Этот проход — проверка что декомпозиция полна.

1. Открываешь оригинальный файл из `tz/` заново — с начала до конца
2. Идёшь по нему абзац за абзацем, предложение за предложением
3. Для каждого требования, пожелания, упоминания, детали — находишь где оно отражено:
   - В каком домене?
   - В какой фиче?
   - В v1, v2 или вне скопа?
   - В какой фазе ROADMAP?
4. Если что-то из ТЗ **не нашлось** ни в одной категории — это потеря. Добавляешь в нужный домен/фичу/скоп
5. Записываешь таблицу трассировки в `REQUIREMENTS.md` секция "Трассировка ТЗ"

**Формат таблицы трассировки:**

```
## Трассировка ТЗ

| Пункт из ТЗ | Домен | Фича | Скоп | Фаза |
|-------------|-------|------|------|------|
| Регистрация через email и Google | Авторизация | Регистрация по email; Логин через Google | v1 | 1 |
| Уведомления о заказах | Уведомления | Push-уведомления о статусе заказа | v2 | — |
```

**Железные правила верификации:**
- Если пункт ТЗ размытый ("и прочее", "а также") — уточни у пользователя что конкретно имелось в виду
- Если пункт ТЗ распался на несколько фич — все фичи должны быть в таблице
- Если пункт ТЗ ушёл в "вне скопа" — это ок, но он должен быть в таблице с пометкой
- **Нулевая толерантность к потерям:** каждая строка ТЗ должна отразиться в таблице

**После верификации:** показываешь пользователю таблицу трассировки и спрашиваешь: "Вот как ТЗ легло на карту. Всё на месте? Ничего не упустил?"

Только после подтверждения пользователя — декомпозиция завершена.

---

## Артефакты декомпозиции

После завершения все 5 файлов должны быть заполнены:

| Файл | Что содержит после декомпозиции |
|------|---------------------------------|
| `REQUIREMENTS.md` | Карта доменов + фичи + v1/v2/вне скопа + таблица трассировки ТЗ |
| `ROADMAP.md` | Фазы + задачи с зависимостями и волнами |
| `PROJECT_CONTEXT.md` | Стек, архитектура, ключевые решения |
| `CURRENT_TASK.md` | Статус: "Декомпозиция завершена. Ждём команду на фазу 1" |
| `tz/[файл].md` | Оригинал ТЗ — не трогается |

---

## После декомпозиции

Декомпозиция завершена — переходишь в режим ожидания. Пишешь пользователю:

```
Карта готова. Когда будешь готов — скажи "делай фазу 1" (или любую другую).
Я возьму фазу из ROADMAP и пройду полный цикл: discuss → исследование → план → Артём → Гриша → Игорь → деплой → Виктор.
```

Пользователь контролирует темп. Ты не начинаешь фазу сам.
